# Architecture

## 목표 흐름

```text
공식 API / 기업 Careers / 검색 발견
              ↓
          수집 어댑터
              ↓
     정규화 + 출처 원문 보존
              ↓
       중복 식별과 공고 병합
              ↓
       저비용 키워드 사전 필터
              ↓
          AI 적합도 평가
              ↓
       운영진 최종 검수 화면
              ↓
        게시용 AI 가공 큐
```

## 설계 원칙

- 플랫폼 페이지보다 공식 API와 기업 원천 공고를 우선한다.
- 자동 수집을 금지한 서비스는 직접 크롤링하지 않는다.
- 원문과 AI 생성 필드를 분리해 추적 가능성을 지킨다.
- 같은 공고가 여러 곳에서 발견되면 하나의 공고에 여러 출처 URL을 연결한다.
- AI 호출 전에 키워드와 명시 규칙으로 후보군을 줄인다.
- 채택 전에는 외부 게시나 자동 발송을 하지 않는다.

## 모듈 경계

| 모듈 | 책임 |
|---|---|
| Collector | 허용된 출처에서 원문 후보 수집 |
| Normalizer | 출처별 필드를 통합 형식으로 변환 |
| Deduplicator | 회사·제목·지역·원문 특징으로 동일 공고 병합 |
| Prefilter | Dreamdurim 핵심 키워드 기반 저비용 필터 |
| Ranker | AI 적합도와 판단 근거 생성 |
| Review | 운영진의 채택·보류·제외 기록 |
| Publisher | 채택된 공고만 게시 형식으로 가공 |

## 현재 저장 모델

- `jobs`: 정규화된 공고 본문과 현재 상태
- `job_sources`: 동일 공고에 연결된 원천 URL과 수집 시각
- `review_decisions`: 운영진 판단과 판단 시각
- `collection_runs`: 출처별 실행 결과와 오류 기록

스키마 변경은 Drizzle 마이그레이션으로만 적용한다. 런타임에서 테이블을 만들거나 수정하지 않으며, 애플리케이션 쿼리는 D1 prepared statement를 사용한다.

## 사람인 수집 흐름

1. 운영 화면 또는 향후 스케줄러가 단일 키워드 수집을 요청한다.
2. 어댑터가 `updated_min`, 수정일 내림차순, 페이지당 110건으로 공식 API를 호출한다.
3. 문자열과 숫자가 섞인 응답 필드를 명시적으로 변환한다.
4. 회사명·공고명·지역 지문으로 기존 공고를 찾고, 동일 공고에는 출처만 병합한다.
5. 신규·병합 건수와 오류를 `collection_runs`에 기록한다.

사람인 API는 공고 전문을 반환하지 않으므로 현재 점수는 키워드 일치에 기반한 사전 점수다. AI 정밀 평가는 별도 `evaluations` 모델을 추가하는 다음 개발 단위로 남긴다.

## 운영 안전장치

- 실제 API 키가 없으면 수집 요청은 명확한 미설정 상태로 종료한다.
- 접근 키는 요청 URL 이외의 로그나 데이터베이스에 저장하지 않는다.
- 원문 응답 전체를 보존하지 않고 정규화된 채용 메타데이터와 원문 URL만 저장한다.
- 샘플 공고에는 `DEMO` 표시를 붙이고 검수 결정을 영속화하지 않는다.
- 사람인 API 기반 데이터의 보존·AI 가공 허용 범위는 실제 운영 전 사람인에 별도 확인한다.
